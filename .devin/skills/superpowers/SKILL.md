# Superpowers — Методология разработки

Источник: [obra/superpowers](https://github.com/obra/superpowers) (MIT)

Superpowers — это набор составных навыков для структурированной разработки: test-driven development (TDD), систематическая отладка, brainstorming, планирование и code review.

---

## 1. Brainstorming — Идеи в дизайн

Используй **перед любой творческой работой** — создание фичей, компонентов, изменение поведения.

**НЕ пиши код, пока дизайн не утверждён.**

### Чеклист

1. **Изучи контекст проекта** — файлы, документация, последние коммиты
2. **Задавай уточняющие вопросы** — по одному, пойми цель/ограничения/критерии успеха
3. **Предложи 2-3 подхода** — с компромиссами и рекомендацией
4. **Представь дизайн** — секциями, масштабированными по сложности
5. **Запиши дизайн-документ** — сохрани в `docs/specs/`
6. **Самопроверка спеки** — проверь на плейсхолдеры, противоречия, неясности
7. **Переход к планированию** — создай план реализации

### Антипаттерн: "Это слишком просто для дизайна"

Каждый проект проходит через этот процесс. Todo-лист, утилита из одной функции, изменение конфига — всё. Дизайн может быть коротким, но он ДОЛЖЕН быть представлен и утверждён.

## 2. Написание планов

Используй когда есть спека или требования для многошаговой задачи, **перед написанием кода**.

### Принципы

- Пиши план как будто инженер имеет **нулевой контекст** кодовой базы
- Каждый шаг — **одно действие (2-5 минут)**
- Точные пути к файлам, полный код в каждом шаге
- DRY, YAGNI, TDD, частые коммиты
- **Никаких плейсхолдеров:** "TBD", "TODO", "implement later" — это провал плана

### Структура задачи в плане

```markdown
### Задача N: [Компонент]

**Файлы:**
- Создать: `exact/path/to/file.py`
- Изменить: `exact/path/to/existing.py:123-145`
- Тест: `tests/exact/path/to/test.py`

- [ ] Шаг 1: Написать падающий тест
- [ ] Шаг 2: Запустить тест, убедиться что падает
- [ ] Шаг 3: Написать минимальную реализацию
- [ ] Шаг 4: Запустить тест, убедиться что проходит
- [ ] Шаг 5: Закоммитить
```

### Самопроверка плана

1. **Покрытие спеки** — каждое требование имеет задачу?
2. **Плейсхолдеры** — нет "TBD", "TODO", обобщённых шагов?
3. **Цепочка зависимостей** — задачи можно выполнять по порядку?
4. **Точность** — пути файлов, команды, ожидаемый вывод?

## 3. Test-Driven Development (TDD)

Используй при реализации **любой** фичи или багфикса.

### Железный закон

```
НИКАКОГО ПРОДАКШН-КОДА БЕЗ ПАДАЮЩЕГО ТЕСТА СНАЧАЛА
```

### Цикл Red-Green-Refactor

1. **RED** — Напиши тест. Запусти. Он ДОЛЖЕН упасть.
   - Если тест проходит сразу — тест бесполезен или фича уже есть
2. **GREEN** — Напиши **минимальный** код, чтобы тест прошёл
   - Не оптимизируй. Не добавляй "пока я тут". Только чтобы прошёл тест
3. **REFACTOR** — Улучши код, сохраняя зелёные тесты
   - Убери дублирование, улучши имена, упрости

### Когда использовать

**Всегда:** новые фичи, багфиксы, рефакторинг, изменения поведения.

**Исключения (спроси пользователя):** одноразовые прототипы, сгенерированный код, конфигурационные файлы.

## 4. Систематическая отладка

Используй при **любом** багфиксе. **Не чини ничего, пока не найдёшь корневую причину.**

### 4 фазы

#### Фаза 1: Расследование
- Воспроизведи баг
- Собери данные: логи, трейсы, состояние
- Определи точные условия, когда баг проявляется

#### Фаза 2: Анализ паттернов
- Что изменилось? Когда началось?
- Какие компоненты задействованы?
- Есть ли паттерн (временной, данных, окружения)?

#### Фаза 3: Тестирование гипотез
- Сформулируй гипотезу о корневой причине
- Спроектируй эксперимент для проверки
- Проверь гипотезу, не изменяя продакшн-код

#### Фаза 4: Реализация
- Напиши тест, воспроизводящий баг (RED)
- Исправь корневую причину (GREEN)
- Убедись, что ничего не сломалось (REFACTOR)

### Защита от зацикливания

Если 3 попытки исправления не помогли → остановись и проведи архитектурный ревью. Возможно, проблема не там, где ты ищешь.

---

## 5. Верификация перед завершением

Перед тем как сказать "готово", проверь:

1. **Все тесты проходят** — запусти полный набор тестов
2. **Линтер чист** — нет ошибок и предупреждений
3. **Сборка работает** — проект собирается без ошибок
4. **Код соответствует спеке** — каждое требование реализовано
5. **Нет TODO/FIXME** в новом коде
6. **Коммиты атомарны** — каждый коммит делает одну вещь
